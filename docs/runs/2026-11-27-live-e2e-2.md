# Live end-to-end run #2 — 2026-11-27 (after the story-gate fixes)

The second real run of the whole app with real LLM calls, after PR #14 (story gates). Same input as
[run #1](2026-11-27-live-e2e.md), so the two can be compared.

**Short version:** it works. The checks caught three mistakes and the LLM fixed them, all 4 evidence
checks pass, and the blind detective found the late supplier on its own. It first scored recall 0.67,
but after fixing two scoring problems (below) the honest score is **0.5**, below the target of 0.6.
Total time: about 4 min 10 s. The run now also replays fully offline in about 5 s.

## The story the LLM built

- **Supplier SUP-001** (laptops) becomes late from **1 March 2025**: the chance of a late delivery jumps
  from 8 % to 60 %.
- From **15 March to 15 April** it also starts short-shipping: the chance of an incomplete delivery rises
  from 5 % to 30 %.
- Nothing else is changed by hand. Lost sales and complaints have to follow from the chain.
- Data: 3 suppliers, 5 stores, 40 products, 800 customers, January to April 2025.

## What the new checks did (the fixes worked)

1. **Story point entity check (A4):** the first story had no entity on 2 story points. It was sent back
   with the suggestion `{"name": "supplier", "ids": ["SUP-001"]}` and fixed on the 2nd try.
2. **Story gate, expectations (A5 try 1):** the scenario compiled, but lost sales *fell* by 62 %. In
   run #1 this would have been accepted. Here it was sent back.
3. **Story gate, warm-up (A5 try 2):** lost sales rose from 2.7 to 9.7 per day *before* the story started.
   This is the same January problem as run #1. It was sent back, and A5 raised the initial stock (now 38–56
   units) on try 3.

## Scoring fixes after this run (`fix/detective-scoring`)

1. **The baseline story point counted against recall.** `sp_baseline` (phase 0, "normal operation") was in
   the answer key, but it is not an event. → Only story points with **phase ≥ 1 and an entity** are scored.
2. **Matching on supplier alone was too loose.** The detective dated the short-shipping to 31 March (real
   start: 15 March, 16 days off, outside the ±14-day window), so that finding did not match. A *different*
   finding (about the 1 March delays, dated 3 March) got matched to the short-shipping point instead.
   → A finding now counts only for the story point **nearest to it in time** among the points about the
   same entity, and that point must still be within ±14 days.

**Rescored: recall 0.5, precision 0.33.** The detective found the late deliveries but dated the
short-shipping too late. That is an honest result, and it is below the eval target of 0.6.

Still open: A5 takes up to 3 tries × ~1 minute. That's fine for the demo, but it is the slow part.

## Offline demo replay

The LLM cache for this run is committed (`.cache/llm/`, 20 files). With `LLM_OFFLINE=1`, the same company
and story text, and the default model `anthropic:claude-sonnet-5-5`, the whole flow replays **with no LLM
calls in about 5 seconds**. That includes the 3 A5 tries, 4/4 evidence and the detective (recall 0.5).
Verified on the `fix/detective-scoring` branch.

- If your local environment file sets `LLM_MODEL` or `LLM_MODEL_<STEP>` to another model, the cache keys
  won't match. Override them for the demo.
- The detective's first step ("list tables") is the same for every dataset, so one cache entry serves all
  runs.
