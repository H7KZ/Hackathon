# Live end-to-end run — 2026-11-27

One real run of the whole app with real LLM calls. Goal: test the parts that can't run offline (the LLM
cascade and the blind detective) plus the UI smoke test.

**Short version:** everything *runs* end to end without crashing (about 3 min 15 s). But the result is
**not good**. The story never got into the data, so 2 of the 5 checks failed and the detective found
nothing. That is caused by two bugs in our checks, listed below. The dataer itself did its job.

## What was run

- `main` at `ecb4e64` (after the dataer PR #12), API started with real services and `LLM_OFFLINE=0`.
- One session, no retries:
  - **Company:** "Elektro Novák s.r.o., řetězec 5 prodejen spotřební elektroniky"
  - **Story:** "Od března začne dodavatel notebooků zpožďovat dodávky. Prodejnám dochází zboží, zákazníci
    odcházejí bez nákupu a přibývá stížností na nedostupnost."
- Steps: create session → cascade writes the scenario → approve → engine generates data → evidence → detective.
- Separately: the Playwright UI smoke test (`pnpm test:e2e`) with fake services, so no LLM.

The key one is the first check: **deliveries did not get later at all.** The two checks that passed are
explained by something else (see "other observations").

### Detective: found nothing (score 0)

It ran 11 queries and correctly reported that *no supplier shows a clear change in lateness*. That is
true for this data, because the story wasn't there. It then picked up noise: a product with fewer orders,
and a jump in lost sales in late January. Score: recall 0, precision 0.

## Why it went wrong

1. **The story curve pointed at nothing.**
   - The scenario's curve `laptop_delay_prob` should make laptop deliveries late from March.
   - Its scope is `{ "field": "day", "ids": ["laptop_delivery"] }`. That means "apply when the day equals
     'laptop_delivery'", which never happens.
   - The engine quietly uses the baseline (5 %) for anything outside the scope
     (`services/noiser/src/engine/curves.ts:40`). So the delay never kicked in.
   - **Gap 1:** the compiler does not check `curve.scope`. It should only allow a field that holds entity
     ids, and only ids that exist.
   - **Gap 2:** the A5 repair loop only compiles the scenario. It never runs the engine and the
     expectations (`services/cascade/src/loop.ts:3`). So a scenario whose story fails gets accepted on the
     first try.

2. **The detective could never score, even with good data.**
   - None of the 4 story points has an `entity` (for example the laptop supplier `SUP-00x`).
   - Scoring needs a finding to name an entity id from the story point.
   - With no ids in the answer key, recall is always 0.
   - **Gap 3:** A4/A5 should be required to set `entity` on the story points that a detective is meant
     to find (at least the phase-1 cause).

## Other observations

- **Lost sales jump in late January.** It happens in every store, well before the story starts. Most
  likely the stores run out of their starting stock (a "warm-up" effect). This inflates the "before"
  period and confuses the detective. Worth a small fix in the scenario defaults, e.g. higher initial stock.
- **"Lost sales" and "complaints" still passed.** That comes from the warm-up effect above, plus the
  check windows. It is not the story, so the evidence checks can pass for the wrong reason.
- **This run wrote 20 new LLM cache files in `.cache/llm/`. They are not committed.** They let this exact run
  replay offline. They are probably not worth committing for the demo, because the run itself is bad.

## Suggested next steps (in order)

1. Compiler: validate `curve.scope.field` and `ids` (Gap 1). This is cheap and would have caught this run.
2. Cascade A5: after compiling, run the engine and the expectations, and send failures back to the LLM
   (Gap 2). AGENTS.md already lists this as an eval gate.
3. Scenario: require `entity` on story points that are meant to be found (Gap 3).
4. Then do one more live run and commit its cache for the offline demo.

## Fixed by `fix/story-gates`

| Problem | Fix |
|---|---|
| Curve scoped by `day` was accepted | Compiler rejects `scope.field: "day"`, entity-like scope ids that don't exist, and a scope field that can't be resolved where the curve is used. A4 runs the same check (`checkStoryRefs`), because A5 copies curves unchanged. |
| A5 accepted a scenario whose story failed | A5 runs a **story gate** after compiling. It runs the engine at the scenario seed, checks the FKs, and runs the expectations. Any failure goes back to A5 with the numbers. |
| Story points without an entity (recall always 0) | Compiler and A4 require an `entity` on every story point that drives a curve, and suggest the curve's scope ids. |
| Warm-up drift in January | The story gate flags an observed table whose daily volume drifts before the story starts (more than 35 % between the halves of the baseline, z > 4), and tells A5 to raise the initial stock or balance supply with demand. |
